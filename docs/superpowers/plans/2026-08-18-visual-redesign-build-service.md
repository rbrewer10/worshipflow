# Visual Redesign — Build Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the Build Service screen — `ServiceEditor.tsx`, `ServiceDeck.tsx`, `ItemEditor.tsx`, and its 12 type-specific editors under `src/renderer/src/editors/` — from raw light-theme Tailwind utility classes to the confirmed dark navy/blue/emerald palette already shipped in the Foundation, TopBar+Home, and Live-tab stages. This is stage 4 of the design spec's rollout order (`docs/superpowers/specs/2026-08-11-visual-redesign-design.md`, Section 4).

**Architecture:** Same conversion as every prior stage: replace raw utility strings (`bg-white`, `border-slate-200`, `text-slate-900`, etc.) with the Foundation stage's semantic tokens. The key difference in this stage: **many files in scope already lean heavily on the shared `.btn*`/`.card*`/`.surface`/`.section-header`/`.badge*` classes and the global bare `input`/`textarea`/`select` rule — all already reskinned dark by the Foundation stage** (`src/renderer/src/assets/main.css`). Two of the twelve editors (`CountdownEditor.tsx`, `TickerEditor.tsx`) turn out to need **zero changes** for exactly this reason — confirmed by reading them, not assumed. Every task below states plainly whether a file needs changes and exactly what they are; don't "improve" things this plan says are already correct.

**Tech Stack:** React, Tailwind CSS v3, the shared component classes from `main.css` (Foundation stage).

## Conversion rules (same as every prior stage — apply consistently)

| Old (light theme) | New (dark theme) |
|---|---|
| `bg-white`, `bg-slate-50`, `bg-slate-100` (panels/inputs/dropdowns) | `bg-panel` (or `bg-panel-raised` for nested/hover/elevated surfaces) |
| `border-slate-200`, `border-slate-300` | `border-border` (or `border-border-strong` for emphasis) |
| `text-slate-900` | `text-content-primary` |
| `text-slate-500`, `text-slate-600`, `text-slate-700` | `text-content-secondary` |
| `text-slate-400` | `text-content-tertiary` |
| `hover:bg-slate-100`, `hover:bg-slate-200` | `hover:bg-panel-raised` |
| A resting state that's ALREADY `bg-panel-raised` needing a hover step lighter still | `hover:bg-border-strong` (established in the TopBar stage's Rehearsal toggle — `panel-raised` is the lightest defined neutral tier, so this is the deliberate way to get a third, visibly-different step) |
| Status-badge/pill **text** at `-700`/`-800` sitting on a translucent tint (`bg-{color}-500/NN`) or a solid light pastel (`bg-{color}-50`/`-100`) | lighten to `-400`; a solid light pastel background also becomes the translucent-tint pattern (`bg-{color}-500/10`) — e.g. `bg-amber-50 text-amber-700 ring-amber-200` → `bg-amber-500/10 text-amber-400 ring-amber-500/30` |
| Bare **text-only** blue (`text-blue-600`/`text-blue-700`, not a solid-fill button) | `text-blue-400` |

Do not touch: shared classes (`.btn`, `.btn-primary`, `.btn-secondary`, `.btn-danger`, `.btn-pill`, `.btn-icon`, `.card`, `.card-lg`, `.card-interactive`, `.surface`, `.section-header`, `.section-title`) — already dark from the Foundation stage, used as-is. Bare `<input>`/`<textarea>`/`<select>` elements with NO explicit color classes of their own also already pick up the dark styling from Foundation's global rule — only touch an input/textarea if it has its OWN explicit `bg-`/`border-`/`text-` classes overriding that global rule. Solid-fill buttons with white/black text on a saturated color (`bg-blue-600 text-white`, `bg-emerald-600 text-white`, `bg-red-600 text-white`) need no change. Do not touch any `useState`/`useEffect`/handler/prop — this is styling-only.

**One new pattern this stage introduces:** a color-swatch picker (`HeaderEditor.tsx`) uses a dark `ring-slate-900` to mark the selected swatch — on a dark app background a near-black ring is invisible. This needs to flip to a light ring (`ring-white`) plus a `ring-offset-panel` utility (generated by Tailwind from the Foundation `panel` token) so the gap between swatch and ring reads as part of the dark surface instead of the browser's default white ring-offset. This is the one place in this stage where the fix isn't "translate slate-* to a token" — read Task 4 carefully.

**One deliberate exception:** the Live Call QR code image (`LiveCallEditor.tsx`) keeps a literal `bg-white` — QR codes need real white-on-black contrast to scan reliably; this is a functional requirement, not a leftover light-theme class. Don't "fix" it.
